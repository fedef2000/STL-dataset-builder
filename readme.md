# NL-to-STL Dataset Builder

A modular, resumable pipeline that builds a dataset of **(Natural Language Requirement, Signal Temporal Logic Formula)** pairs from the Cyber-Physical Systems (CPS) and formal verification literature. It discovers academic papers on Signal Temporal Logic (STL), downloads their LaTeX sources or PDFs, audits their licences, finds the STL formulas in them, has language models extract the requirement each formula states, and builds the dataset from their answers. Finally every formula is normalized into one STL syntax, that of `stl-nl`: the formulas without a requirement become the input of `stl-nl`, a tool that writes natural-language descriptions of STL formulas, and the paired ones, with their descriptions, are written in the same syntax for fine-tuning. The final dataset is made of three sets of (description, formula) pairs: both from the papers, the paper's formula with a description by `stl-nl`, and both generated by `stl-nl`; the paper descriptions are judged by language models first, and only those that describe their formula faithfully are kept.

| Step | Script | What it does | Writes |
|---|---|---|---|
| 1 | `01_build_corpus.py` | Discovers papers (citations of the foundational STL papers, keyword searches) and finds their arXiv IDs and PDF links | `data/corpus.json` |
| 2 | `02_download_papers.py` | Downloads the LaTeX source of each paper, or its open-access PDF | `data/raw/` |
| 3 | `03_audit_and_print_licenses.py` | Finds the licence of each downloaded paper | `data/corpus.json` |
| 4 | `04_estimate_formulas.py` | Counts and locates the STL formulas of each paper | `data/corpus.json` |
| 5 | `05_extract_requirements.py` | Two models (a third on their disagreements) give the requirement of each formula; the formulas with a requirement and those without are written from their vote | `data/processed/extractions/`, `data/extracted/` |
| 6 | `06_normalize_formulas.py` | Normalizes every formula into the STL syntax of `stl-nl`: the unpaired ones as its input, the paired ones (and their descriptions) for fine-tuning | `data/normalized/` |
| 7 | `07_finalize_dataset.py` | Builds the final dataset: two models (a third on their disagreements) judge whether each paper description describes its formula and how faithfully; the pairs are written by label | `data/processed/judgments/`, `data/dataset/` |

**Current state:** steps 1-6 are implemented. Step 7 writes the three sets of the dataset (`data/dataset/set_1/`, `set_2/`, `set_3/`) and judges the first; the judgment of the other two and the analysis of the dataset are not implemented yet. The corpus, the extracted and normalized formulas and the dataset are tracked in git (`data/corpus.json`, `data/extracted/`, `data/normalized/`, `data/dataset/`); the downloaded papers and the answers of the models are not (`data/raw/`, `data/processed/`).

## Installation & Configuration

### 1. Install Dependencies

Requires Python 3.10 or newer. Create a virtual environment and install the required packages:

```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux / macOS
source .venv/bin/activate

pip install -r requirements.txt

# Only to run the tests of steps 6 and 7
pip install pytest

```

* `requests`: all HTTP calls.
* `pymupdf`: reads PDF text and metadata (license audit, formula estimation).
* `openpyxl`: writes the `.xlsx` files of step 7.
* `truststore`: makes Python check HTTPS certificates with the operating system's certificate store, like a browser. Without it the pipeline still runs, but some repositories that send an incomplete certificate chain fail with `SSL Certificate Error`.

### 2. Configure `.env`

Copy `.env.example` to `.env` and fill in your email address and (optionally) your API keys. `.env` is gitignored and is loaded by `config.py`; variables already set in the environment take precedence over the file:

```bash
USER_EMAIL=your.name@university.edu        # Enables OpenAlex Polite Pool
OPENALEX_API_KEY=your_free_openalex_key    # Optional: Increases daily quota 10x (get at openalex.org)
SEMANTIC_SCHOLAR_API_KEY=your_s2_key       # Optional: Lifts the anonymous rate limit (semanticscholar.org/product/api)
OPENROUTER_API_KEY=your_openrouter_key     # Step 5 only: the models are called and billed through openrouter.ai

```

Without a Semantic Scholar key, the enrichment lookups of step 1 are likely to be refused; `--mode enrich` reports the state of that service when it starts. The OpenAlex key is sent to OpenAlex only.

## Pipeline Usage

Steps 1 to 4 read from and update **`data/corpus.json`** incrementally; steps 5 and 6 read the outputs of the step before (see each step). You can interrupt (`Ctrl+C`) and resume any script at any time without losing progress: step 5 keeps every answer as it arrives, and its `data/extracted/` and step 6 are rebuilt whole in a minute or two.

Every script also accepts `-h` / `--help`, which prints its flags and exits.

Steps 1 to 4 can print their statistics from `data/corpus.json` without redoing the work: `--stats` on any of the four scripts. Step 5 has `--no-calls` for the same: it makes its report and `data/extracted/` again from the stored answers.

### Step 1: Build & Expand the Paper Corpus

Step 1 gathers everything that is known about the papers, without downloading them. It discovers papers via 1-hop foundational citations, 2-hop citation cycles, or keyword searches, and then asks other services for the arXiv IDs and PDF links that OpenAlex does not list:

```bash
# 1A. Fetch Hop-1 papers citing the 4 foundational STL papers
python scripts/01_build_corpus.py --mode citations --hops 1

# 1B. Expand to Hop-2 (papers citing Hop-1 papers that have >= 5 citations)
python scripts/01_build_corpus.py --mode citations --hops 2 --min-hop1-citations 5

# 1C. Discover additional preprints and papers via keywords (arXiv + OpenAlex)
python scripts/01_build_corpus.py --mode keywords --keywords "Signal Temporal Logic" "Metric Temporal Logic" "STL specification"

# 1D. Enrich the corpus with missing arXiv IDs and PDF links (Semantic Scholar, arXiv title search, HAL)
python scripts/01_build_corpus.py --mode enrich

# Run all modes together
python scripts/01_build_corpus.py --mode all --hops 2

# Show the discovery statistics of the existing corpus
python scripts/01_build_corpus.py --stats

# Merge entries that turned out to be the same paper
python scripts/01_build_corpus.py --merge-duplicates

```

| Flag | Default | What it does |
|---|---|---|
| `--mode {citations,keywords,enrich,all}` | `citations` | What to run: the citation crawl, the keyword search (arXiv + OpenAlex), the enrichment (see below), or the three in that order. |
| `--hops {1,2}` | `1` | Citation depth. `1` fetches (or refreshes) the papers citing the 4 seed papers. `2` also fetches the papers citing those Hop-1 papers; Hop-1 itself is only fetched if it is not in the corpus yet. Ignored with `--mode keywords`. |
| `--min-hop1-citations N` | `5` | With `--hops 2`: only Hop-1 papers with at least `N` citations are expanded. |
| `--hop2-require-stl-text` / `--no-hop2-require-stl-text` | on | With `--hops 2`: keep a Hop-2 paper only if its title or abstract matches the STL relevance terms. The `--no-` form keeps every Hop-2 paper (much larger, off-topic corpus). |
| `--limit N` | none | With `--mode enrich`: asks each service about at most `N` papers (for testing). |
| `--stats` | off | Prints the statistics of the existing corpus (hops, discovery methods, metadata, enrichment lookups), then exits. No API is queried. |
| `--merge-duplicates` | off | Merges entries of the existing corpus that share an arXiv ID or a DOI, then exits. The published OpenAlex record is kept, the other ID is recorded under `alternate_ids`, and the duplicate download is deleted. No API is queried. |
| `--keywords K [K ...]` | `"Signal Temporal Logic" "STL specification" "STL formulas"` | Search phrases for the keyword search. Quote each phrase. Ignored with `--mode citations`. |

#### Enrichment

`--mode enrich` asks three services about the papers of the corpus. It can be interrupted and re-run: it only asks what is still unanswered.

| Service | Asked about | How | Gives |
|---|---|---|---|
| Semantic Scholar | Every paper with a DOI | 500 papers per request | arXiv ID, open PDF link |
| arXiv title search | Papers with no arXiv ID | 15 papers per request, one request every 3 seconds | arXiv ID |
| HAL | Papers with no arXiv ID that are not downloaded yet | One request per paper | Open PDF link |

Each answer is stored under the paper's `lookups` field as `found`, `not_found` or `no_answer`. `no_answer` means the service was rate-limited or unreachable, and that paper is asked again on the next run. A service that keeps rate-limiting is left alone for 15 minutes.

When a lookup gives a new arXiv ID or PDF link to a paper that step 2 had marked `unavailable`, the paper goes back to `pending`, so the next run of step 2 tries it. If the arXiv ID found already belongs to another entry, the two entries are the same work and are merged (as with `--merge-duplicates`).

### Step 2: Download Papers Locally (`.tex` & `.pdf`)

Downloads raw LaTeX source files (`data/raw/latex/{paper_id}/`) whenever available on arXiv, or falls back to Open Access PDFs (`data/raw/pdfs/{paper_id}.pdf`). It only uses the links that step 1 stored in the corpus and does not look for new ones:

```bash
# Download every paper that has not been tried yet
python scripts/02_download_papers.py

# Show the download status of the whole corpus
python scripts/02_download_papers.py --stats

# Go back over papers that failed on a network problem or a server error
python scripts/02_download_papers.py --retry-transient

# Fetch the LaTeX source of the papers held as PDF for which an arXiv ID is now known
python scripts/02_download_papers.py --upgrade-pdfs

```

Each run first compares `data/corpus.json` with the files on disk and corrects the recorded status. Without any flag, only `pending` papers are downloaded: those never tried, and those for which the enrichment of step 1 found a new link.

| Flag | What it does |
|---|---|
| `--retry-unavailable` | Also retries **every** paper marked `unavailable`, whatever the reason. |
| `--retry-transient` | Also retries the `unavailable` papers whose failure reason is a connection error, a timeout, HTTP 429 or HTTP 500/502/503/504. |
| `--upgrade-pdfs` | Only goes over the papers held as PDF that have an arXiv ID (usually found by the enrichment after the PDF was downloaded) and fetches their LaTeX source, one request every 3.5 seconds, then prints a report and exits. When the source is downloaded, the paper's PDF is deleted. A paper for which arXiv has no LaTeX source is recorded under `local_files.latex_upgrade` and not asked again; a network failure is tried again on the next run. Run steps 3 and 4 afterwards. |
| `--delay S` | Seconds to pause after each arXiv download (default 3.5), in the normal run and with `--upgrade-pdfs`. When arXiv answers HTTP 429 or 503, the same paper is tried again after 30, 60, 120 and 300 seconds and the pause between papers doubles (up to 30 seconds); it halves again after 10 papers without a refusal. If arXiv still refuses after the last wait, the run stops and reports how many papers were not tried; the paper it stopped on is left untouched, with no fallback to its PDF. A dropped connection or a timeout is tried once more after 10 seconds. |
| `--limit N` | Processes only the first `N` papers of the queue (for testing). |
| `--stats` | Prints the status counts and failure reasons of the whole corpus, then exits. Nothing is downloaded. |
| `--relabel` | Rewrites the stored failure reasons in the current wording, prints the same report as `--stats`, then exits. Nothing is downloaded. |

`--retry-transient` is redundant with `--retry-unavailable`, which already includes those papers. `--stats` and `--relabel` take precedence over all the download flags, and `--upgrade-pdfs` over the retry flags.

#### Failure reasons

A paper that could not be downloaded gets `status: "unavailable"` and one of these `failure_reason` values in `data/corpus.json`. Reasons from PDF links are prefixed with `PDF Mirrors: ` and describe the last link tried.

| Failure reason | Meaning |
|---|---|
| `No Link Found (not open access)` | No arXiv source and no PDF link is known, and the paper is not open access. Nothing was attempted. |
| `No Link Found (open access, but no URL listed)` | Same, for a paper that OpenAlex marks as open access. |
| `No Link Found (a lookup got no answer, run the enrichment again)` | No link is known, but an enrichment lookup of step 1 got no answer for this paper, so one may still exist. |
| `arXiv Error: HTTP 404 (Not Found)` / `HTTP 403 (Forbidden/Blocked)` / `HTTP <code>` | arXiv refused or does not have the source bundle. |
| `arXiv Error: Connection Timeout` | arXiv did not answer in time. |
| `arXiv Error: Network/System Exception (<error>)` | Any other problem while fetching or unpacking the arXiv bundle. The brackets name the error and the one underneath it, e.g. `(ConnectionError: NameResolutionError)` for a DNS failure or `(SSLError: SSLCertVerificationError)` for a certificate problem. |
| `Archive contained no .tex files` | The arXiv bundle was unpacked but holds no LaTeX. |
| `Invalid archive format or PDF only` | arXiv only has a PDF for this paper, or the bundle could not be read. |
| `HTTP 403 (Paywall or Bot Protection)` | The host refuses automated downloads. |
| `HTTP 404 (Dead Link)` / `HTTP 410 (Removed by Host)` | The file is gone. |
| `HTTP 401 (Login Required)` | The host asks for an account. |
| `HTTP 202 (Bot Protection Challenge)`, `HTTP 405`/`406`/`418 (Bot Protection)` | The host answered with an anti-bot page instead of the file. |
| `HTTP 429 (Rate Limited)` | The host asked to slow down. |
| `HTTP <code>` (e.g. 500, 502, 503) | Any other answer from the host, usually a server-side error. |
| `HTML Landing Page (Not a %PDF file)` | The link returned a web page instead of a PDF. |
| `Connection Timeout` | The host did not answer in time. |
| `SSL Certificate Error` | The host's HTTPS certificate is invalid (for example expired). |
| `Connection Error (Domain unreachable)` | The host could not be reached at all. |

The `--stats` report also counts the unavailable papers that still have an unanswered lookup, whatever their failure reason.

### Step 3: Audit Exact Licenses & Print Statistics

Scans local `.tex` files, PDF metadata, and arXiv OAI-PMH headers to verify exact paper licenses, flags any conflicts with OpenAlex metadata, updates `data/corpus.json`, and prints a full breakdown report:

```bash
python scripts/03_audit_and_print_licenses.py

# Print the report again without re-scanning
python scripts/03_audit_and_print_licenses.py --stats

# Re-derive licence names and tiers from the licences already stored (after a change to the patterns), no scan
python scripts/03_audit_and_print_licenses.py --reclassify

```

| Flag | What it does |
|---|---|
| `--stats` | Skips the scan and prints the report from the licences already stored in `data/corpus.json`, then exits. |
| `--limit N` | Audits only the first `N` downloaded papers (for testing). The report still covers the whole corpus. |
| `--reclassify` | Skips the scan: turns the licences already stored into their short names (`cc-by`, ...), sets the tier and the conflict flag again, saves `data/corpus.json` and prints the report. For a change to the licence patterns or tiers, without asking arXiv again. |

### Step 4: Estimate STL Formula Yield

Scans all downloaded `.tex` folders and `.pdf` files, counts the temporal operators with a time bound and the formulas they form (concrete and symbolic) per paper, saves the counts under `formula_estimates` in `data/corpus.json`, and prints the 20 papers with the most concrete formulas:

```bash
python scripts/04_estimate_formulas.py

# Print the report again without re-scanning
python scripts/04_estimate_formulas.py --stats

```

| Flag | What it does |
|---|---|
| `--limit N` | Scans only the first `N` downloaded papers (for testing). |
| `--stats` | Prints the same report from the estimates already stored in `data/corpus.json`, then exits. No file is scanned. |

### Extraction: what the model reads

The first part of the extraction is the context builder (`src/extraction/context.py`), which decides what the model reads about a paper held as LaTeX:

* **Header:** the title and the abstract of the paper.
* **Regions:** pieces of one `.tex` file around the concrete formulas found in step 4. A region starts about 2,000 characters before a formula and ends about 3,000 after it, at paragraph ends, and stays inside the formula's `\section`. Formulas that lie close together share a region, so the same text is not sent once per formula; a run of more than 15 formulas is split into several regions.
* **Formula IDs:** every formula is numbered (`F1`, `F2`, ...) and wrapped in `⟦F1⟧ ... ⟦/F1⟧` in the text given to the model, which answers once per ID.

```bash
# Coverage of the evaluation set: is every labelled formula marked, and its requirement inside the same region?
python scripts/eval/check_contexts.py

# Print the regions of one paper as the model sees them
python scripts/eval/check_contexts.py --paper W4410555912

# Regions, formulas and input tokens over every LaTeX paper of the corpus
python scripts/eval/check_contexts.py --corpus
```

| Flag | What it does |
|---|---|
| `--entry EVAL_NN` | Prints the one region the model reads for an entry of the evaluation set, with the labelled formula pointed out and the label above it. Use it to review a label. |
| `--paper ID` | Prints the header and every region of one paper, with every concrete formula step 4 found (the evaluation set labels only a few of them). Long regions are shortened unless `--full` is given. |
| `--corpus` | Reports the size of the job over the whole corpus instead of the evaluation set. |
| `--before N`, `--after N` | Characters of context before and after a formula (default 2000 and 3000). |
| `--max-formulas N` | Most formulas marked in one region (default 15). |
| `--symbolic` | Also marks the formulas whose time bounds are all symbolic. |

### Step 5: Extract the Requirements

One request per region goes to a model through [OpenRouter](https://openrouter.ai) (`src/extraction/extractor.py`). For every marked formula the model returns the formula, every passage of the paper that states what it requires (a paper may state it more than once in different words; possibly none), each tagged `specific` or `generic`, the application domain from a fixed list, and the meaning of the variables.

A requirement passage is `specific` when it carries the particulars of its formula (numbers, thresholds, time bounds, named regions), e.g. "the vehicle must reach the goal within 10 seconds", and `generic` when it only says what the formula is for, e.g. "the vehicle reaches a goal location within a certain time limit". The test: if the numbers of the formula were replaced by others and the passage would still fit, it is generic. Every specific passage is reported; a generic one is reported only when the paper has no specific one for the formula. The tag lets the final dataset be sorted by quality.

Two models answer every region: Gemini 3.8 Flash with reasoning off and GPT-6 Luna with medium reasoning, chosen with the benchmark below. Where they disagree, `--tie-break` asks a third one, Claude Sonnet 5.5 with medium reasoning. The third model is not shown the two answers: it is asked the same question about every region that holds a disputed formula. The answers are then put to a vote (see *How a formula is decided*). The script needs `OPENROUTER_API_KEY` in `.env`.

```bash
# The two models over every region not answered yet, concrete and parametric formulas, then the summary
python scripts/05_extract_requirements.py

# Also the third model, on the formulas the two disagree on
python scripts/05_extract_requirements.py --tie-break

# How many calls a run would make, and about what they cost (no call is made)
python scripts/05_extract_requirements.py --tie-break --dry-run

# The summary and data/extracted/ from the stored answers, without calling a model
python scripts/05_extract_requirements.py --no-calls

# The report of one kind of formula; --details adds its technical tables
python scripts/05_extract_requirements.py --no-calls --concrete
python scripts/05_extract_requirements.py --no-calls --parametric --details

# Only one paper, and print its answers; with --dry-run, print its prompts instead
python scripts/05_extract_requirements.py --paper W3080701220
```

Every answer is appended to `answers.jsonl` as it arrives, so an interrupted run (Ctrl+C included) continues where it stopped. An answer stored for a region whose formulas have since changed is asked again, and so is one that left some formulas of its region unanswered. A run over the whole corpus (with or without `--no-calls`) also writes `data/processed/extractions/formulas.jsonl`: one record per formula with its source, the answer of each model and the outcome of the vote. A run over the whole corpus and every kind of formula also writes `data/extracted/` from the vote (see *The extracted formulas* below).

#### Where the answers are kept

```
data/processed/extractions/
├── latex/
│   ├── concrete/      answers.jsonl, formulas.jsonl
│   └── parametric/    answers.jsonl, formulas.jsonl
└── pdf/
    ├── concrete/      answers.jsonl, formulas.jsonl
    └── parametric/    answers.jsonl, formulas.jsonl
```

`answers.jsonl` holds every answer as the models gave it, one line per call; `formulas.jsonl` holds one record per formula, with every answer and the outcome of the vote. Each source and kind of formula has its own folder: an answer is stored under the number of its region, and the regions of a paper are numbered separately for each source and kind, so in one file the answers of two kinds would be taken for one another.

#### The report

Without `--concrete` or `--parametric`, the script works on both kinds of formula and prints a summary with a column for each and one for the total:

```
RESULT                              what goes into data/extracted/
  formulas with a requirement       specific, generic, or "the models split" on the kind
  formulas without a requirement
  undecided                         the models disagree, or a model has not answered yet
  papers with a requirement         the total counts a paper once

HOW EACH FORMULA WAS DECIDED
  the two models agree              on the same passages, or on none
  they disagree on the requirement  decided by the third model / undecided after it / not asked yet
  same passage, kind disputed       third model not asked yet

COST                                dollars per model
NOTES                               what is left to do, and how many answers failed a check
```

`--concrete` or `--parametric` (or both) restricts the run to that kind of formula and prints its own report instead: the same sections with the number of calls per model. `--details` prints that report for each kind with its technical tables: the answers per model, the failed checks by kind, how the two models agree, and what the third model says about the disputed requirements.

#### Concrete and parametric formulas

The concrete formulas (numeric time bounds) and the parametric ones (time bounds given as symbols, e.g. `G_{[0,T]}(v < v_{max})`) are extracted apart: a plain run does the concrete ones first, then the parametric ones, and `--concrete` or `--parametric` does only one of them:

```bash
python scripts/05_extract_requirements.py --parametric --tie-break
```

When the parametric formulas are extracted, only they are marked and asked about; the concrete ones stay in the text as context. Two things differ from the concrete formulas:

* The formulas are numbered `P1`, `P2`, ... instead of `F1`, `F2`, ..., so an ID stands for one formula of a paper only.
* The prompt tells the two kinds of requirement apart without numbers: a passage is specific when it expresses the formula, naming a parameter where a concrete formula has a number, and generic when it only says what the formula is for. The models are also asked to explain the parameters among the variables.

#### Papers held as PDF

The papers held only as a PDF go through the same steps, with `--pdf` (`--latex` selects the papers held as LaTeX; a plain run does both). A PDF has no math markup, so its region is a page:

* The text of the page, extracted from the PDF (`src/extraction/pdf_context.py`), with the end of the previous page and the start of the next (1,500 characters each): a requirement often sits just before a formula that opens a page.
* The image of the page (150 dpi). The extracted text garbles formulas (flattened subscripts, symbols turned into other characters, a displayed formula broken into pieces), so the model reads each formula from the image.
* A formula is a line of the text on which step 4 finds a bounded temporal operator. The line is marked, and the list of formulas names the operator of each (e.g. `F2 (the formula with ♦[1,2))`), since a line can hold pieces of two formulas.

Two things differ from the LaTeX papers:

* The formula is transcribed into LaTeX by the model, not copied. Instead of the copy check, it must hold the numeric time bounds of at least one operator of its line, as step 4 reads them (`bounds` among the checks; one is enough, since a line can hold several formulas), and the vote keeps a transcription only when two models give the same one (spacing, fonts and synonyms such as `\square` and `\Box` aside): `final.formula`, with `final.formula_given_by`. A displayed formula broken over two lines of the text is marked twice; the second record gets `final.same_formula_as`.
* The requirement passages are copied from the text of the page, as for LaTeX, and checked against it; a word hyphenated at a line end, typographic characters (minus sign, quotes), LaTeX commands written for the characters the text has (`\\varphi` for φ, `\\in` for ∈), fonts and the marks of sub- and superscripts are not compared.

A record of a PDF formula has `source_type` `pdf`, `file` the PDF and `line` the page.

#### How a formula is decided

First the two answers are compared. Two passages are the same when they share at least half of the shorter one.

| Agreement | Meaning |
|---|---|
| `same passages` | Both give the same requirement passages. |
| `both none` | Both find no requirement. |
| `partly the same` | Some passages are shared, but one model gives a passage the other does not. |
| `different passages` | Both give a requirement, with no passage in common. |
| `one gives none` | One model gives a requirement and the other none. |
| `not answered` | A model has no answer for the formula (failed call, formula skipped). |

The three middle cases are disputed (`dispute` is `requirement` in the record), and so are the formulas with the same passages tagged specific by one model and generic by the other (`dispute` is `kind`), and, for a PDF, those with the same passages but a different transcription of the formula (`dispute` is `formula`). With `--tie-break`, the third model is asked about every region that holds a disputed formula, and the record gets a `tie_breaker` field with its answer and its verdict: `sides with the first` / `sides with the second` (the same requirement as that model, or none as it), `agrees with both`, `partly agrees` (a passage shared with one of them, but not all), `agrees with neither`. A region is sent whole, so the third model also answers its other formulas.

Then the answers are put to a vote, passage by passage. Every record has a `final` field with its result:

| Field of `final` | Meaning |
|---|---|
| `outcome` | `requirement` when at least one passage is given by two models; `none` when no passage is and two models give none; `open` (undecided) otherwise. |
| `requirements` | The passages kept, each with its `text`, its `kind`, the model the text is taken `from` and the models it is `given_by`. The text comes from a model whose passage is a copy of the source, the third model first. |
| `kind` | `specific` when a kept passage is specific, `generic` when all are, `unclear` when the models that give a passage are split on its kind, `none` without a requirement. A generic passage is dropped when a specific one is kept. |
| `domain` | The domain most models give; that of the first model when they all differ. |
| `variables` | The symbols explained by any model, with the meaning of the first one that explains them. |
| `models` | How many models answered the formula (2, or 3 where the third model was asked about its region). |

#### Checks on the answers

Every answer is checked, and an answer that fails a check is flagged: the formula and each requirement passage must be copies of the source, every marked formula must be answered once, a specific and a generic passage may not be given together, the domain must be one of the list, and each explained symbol must appear in the formula. Layout is not compared (spacing, line and row breaks, math delimiters, quotation marks, a sentence end at the edge of a passage), and neither is the way a symbol is written (its font, `p_2` against `p_{2}`, one member of an indexed family against another, such as `x_3` in a formula over `x_i`). A passage made of up to three pieces of the excerpt, in their order, is flagged as joining separate parts rather than as not being a copy. The checks are run again on the stored answers at every report, so a change to them needs no new call to the models.

| Flag | What it does |
|---|---|
| `--tie-break` | Also asks the third model about the disputed formulas (requirement or kind). |
| `--concrete` | Only the concrete formulas, with their own report instead of the summary. |
| `--parametric` | Only the parametric formulas, with their own report instead of the summary. With `--concrete`: both, each with its own report. |
| `--latex` / `--pdf` | Only the papers held as LaTeX / as PDF only, with their own reports instead of the summary. |
| `--no-calls` | Uses only the stored answers: no model is called. The vote, the checks, the summary (or the report of `--concrete` / `--parametric`), `formulas.jsonl` and `data/extracted/` are made again from them. |
| `--licenses TIER ...` | Also writes copies of `paired.jsonl` and `unpaired.jsonl` with only the records of these licence tiers (`permissive_cc`, `restricted_cc`, `custom_or_arxiv`, `unspecified`). |
| `--details` | Prints the report of each kind of formula with its technical tables. |
| `--dry-run` | Prints how many calls a run would make and about what they cost (at the average cost of the stored calls of each model), and exits. With `--paper`, also prints the prompts. |
| `--paper ID` | Only this paper (repeatable). Its answers, and the passages the vote keeps, are printed. |
| `--limit N` | Only the first `N` papers. |
| `--models ID[:REASONING] ID[:REASONING]` | The two extraction models, each with an optional reasoning level (`off`, `minimal`, `low`, `medium`, `high`). Default: `google/gemini-3.8-flash:off openai/gpt-6-luna:medium`. |
| `--tie-breaker ID[:REASONING]` | The third model. Default: `anthropic/claude-sonnet-5.5:medium`. |
| `--workers N` | Calls made at the same time (default 8). |
| `--budget D` | Stops starting new calls once `D` dollars are spent in this invocation, by all the models and over both kinds of formula (default 20). |

# The formulas the vote leaves undecided, with the answer of every model and why no two agree

#### Choosing a model: the benchmark

`scripts/eval/benchmark.py` runs several models over the evaluation set and compares how many answers are right, how long a call takes and what it costs. Only the regions that hold a labelled formula are sent (57 calls per model, reasoning level and run).

```bash
# Run what is missing, then print the comparison (five models, reasoning off and medium, Claude Sonnet 5.5 at medium only, three runs each)
python scripts/eval/benchmark.py

# Score the stored answers again without calling any model, e.g. after correcting a label
python scripts/eval/benchmark.py --report

# A quick, cheap trial
python scripts/eval/benchmark.py --name trial --entries 8 --models z-ai/glm-5.3-flash --reasoning off --runs 1
```

Answers are stored in `data/processed/benchmark/<name>/answers.jsonl` as they arrive, so an interrupted run continues where it stopped. `report.md` in the same folder holds the comparison table, the entries where most models disagree with the label (check those labels first) and the variable meanings side by side.

How an entry is scored:

* **Requirement:** right when the label is "none" and the model gives none, or when the model gives every labelled passage and nothing else (a label lists all the passages that state the requirement). Two passages match when they share at least half of the shorter one. `exact` counts the answers whose passages are nearly identical to the labels, `partly` the ones with a passage left out or an extra one, `invented` a requirement given for a "none" label, `missed` a "none" given for a labelled requirement. `Passages found` and `Extra passages` count single passages over the whole set, and `Kind right` the found passages that were given the kind (`specific` or `generic`) of their label.
* **Domain:** the same domain as the label.
* **Variables:** the share of the labelled symbols the model explained. The meanings are not graded.

When a paper prints the same formula more than once, the entry is scored on the occurrence its requirement stands next to.

| Flag | What it does |
|---|---|
| `--models ID ...` | OpenRouter model IDs (default: Claude Sonnet 5.5, Gemini 3.8 Flash, DeepSeek V4.1 Flash, GLM 5.3 Flash, GPT-6 Luna). |
| `--reasoning LEVEL ...` | Reasoning levels tried for every model. Without it, every model runs at `off` and `medium`, except Claude Sonnet 5.5, which runs at `medium` only because it answers the same at every level. A model that cannot switch reasoning off runs `off` as `minimal`, and the table says so. |
| `--runs N` | How many times every model answers the whole set (default 3); answers vary between runs. |
| `--name NAME` | Folder under `data/processed/benchmark` (default `main`). |
| `--workers N` | Calls made at the same time (default 8). |
| `--budget D` | Stops starting new calls once `D` dollars are spent in this invocation (default 15). |
| `--entries N` | Only the first `N` entries of the evaluation set. |
| `--report` | Scores the stored answers and prints the comparison. No model is called. |

#### The extracted formulas

At the end of a run, step 5 writes the formulas from the vote (`src/extraction/dataset.py`) to `data/extracted/`: one record per formula with a requirement, in `paired.jsonl`, and one per formula without a requirement, in `unpaired.jsonl`. They are not yet the final dataset: step 6 writes their formulas in one syntax, and the unpaired ones go to `stl-nl` for a description. With `--no-calls` they are rebuilt from the stored answers at any time; the same answers give the same files.

```bash
# data/extracted/ again from the stored answers (after a change to the checks or to the rules below)
python scripts/05_extract_requirements.py --no-calls

# Also copies with only some licence tiers: data/extracted/paired_permissive_cc.jsonl
# and data/extracted/unpaired_permissive_cc.jsonl
python scripts/05_extract_requirements.py --no-calls --licenses permissive_cc
```

The files are written only by a run over the whole corpus and every kind of formula (no `--paper`, `--limit`, `--concrete`, `--parametric`, `--latex` or `--pdf`): a formula repeated in a paper is kept once over all of them, so a part would give other files. A run whose calls the budget stopped leaves the files as they are, so that it never holds the answers of half a run; run again to continue. A formula still without an answer of a model (a call that failed) is left out as undecided, and the run says how many there are.

A formula is in `paired.jsonl` when the vote of step 5 gives it a requirement. It is left out (and listed in `excluded.jsonl` with the reason) when:

* no two models agree on its requirement (undecided);
* it comes from a PDF and no two models transcribe it alike, or it is the second line of a formula broken over two lines of the PDF text;
* it is an operator alone, without what it applies to (e.g. `\square_{[0,1]}`);
* its requirement is not in English;
* the same paper has the same formula with the same requirement elsewhere: it is kept once, and the record lists the other places in `also_at`.

The formulas the models agree have no requirement go to `unpaired.jsonl`: definitions, examples, templates, proof steps, and formulas the paper does not explain. They are of no use for fine-tuning on (requirement, formula) pairs, but can serve as a corpus of real formulas (e.g. to test a parser), as negative examples for telling requirements apart, or for generating text from a formula with its domain and variables. The same rules leave formulas out of this file (the undecided ones are in neither file), with two differences: a formula repeated within a paper is kept once whatever its passages, and a formula the paper also has with a requirement is left out, as it is in `paired.jsonl` already.

A record (the same in both files):

| Field | Content |
|---|---|
| `id` | `<paper_id>:<formula ID>`, e.g. `W2082084336:P5` (`F` for numeric, `P` for symbolic bounds: the concrete and parametric formulas of steps 4 and 5) |
| `formula` | The formula in LaTeX. From a LaTeX paper: the paper's own text, trimmed to the formula by a model's copy, with labels, row breaks, alignment marks and spacing commands taken out (the authors' macros are kept). From a PDF: the transcription two models agree on. |
| `requirements` | The requirement passages, each with its `text` (on one line) and `kind` (`specific`, `generic`, or `unclear` when the models are split); empty in `unpaired.jsonl` |
| `domain`, `variables` | The application domain, and the meaning of the symbols |
| `bounds` | `numeric` when a time bound at least is a number (`\Box_{[0,5]}`), `symbolic` when every one is a symbol (`\Box_{[0,T]}`). A description of the formula, not a measure of the pair: a symbolic formula whose requirement explains its parameters is as good a pair as a numeric one. |
| `paper_id`, `title`, `year`, `doi`, `arxiv_id` | The paper |
| `license_tier`, `license` | The licence tier (see *License Tiers*) and the licence that sets it (`cc-by`, `arxiv-nonexclusive`, ...): when a paper has several, the most restrictive one |
| `source_type`, `location` | `latex` with the file and line, or `pdf` with the file and page |
| `provenance` | How the formula was obtained, the models that give the requirement (and for a PDF the formula), `disputed` (the first two models disagree on the formula; the third model may be among the models giving the requirement even when it is not, as it answers every formula of a region it is asked about), and `flags`: the checks failed by the answers the passages are taken from, and a formula that starts or ends with a connective (part of it may be on another row) |

`stats.md` counts the records by licence and domain, the requirement passages by kind, the records with a specific passage (the best quality subset for fine-tuning) and their licence tiers, the formulas without a requirement, and the formulas left out by reason. Formulas in another logic (past-time, spatial, probabilistic, ...) are not marked here: the parser of step 6 rejects them. In `excluded.jsonl`, `outcome` is the vote of step 5 for the formula: `requirement`, `none` or `open` (undecided). It has no date, so a rebuild with the same answers leaves it unchanged.

### Step 6: Normalize the Formulas into the Syntax of stl-nl

Writes every formula extracted by step 5 in one STL syntax, that of `stl-nl`, so that the final dataset has all its formulas written the same way. The two files of `data/extracted/` are normalized in the same run, with the same rules, each in its mode:

* **unpaired** (`data/extracted/unpaired.jsonl`, mode `stl-nl`): the formulas become the input of `stl-nl`, described below.
* **paired** (`data/extracted/paired.jsonl`, mode `faithful`): the formulas keep the paper's requirement and go to fine-tuning with it, so they must keep the meaning it describes. Same rules, except that the bounds stay as the paper writes them (`F[0,2.5]`, `F(2,12]`, `G[T,T + delta]`), powers with an integer exponent stay (`x^2`), and the two rules that would change the meaning (an operator with a line over it read as the plain one, a cut formula closed) reject the formula. So these formulas may go beyond `stl-nl`'s grammar (four additions, listed in `docs/normalization_rules.md`) and are not checked with `stlgen`; their skeleton comes from their own tree. Each requirement passage is written to match its formula: plain text, every symbol as the formula writes it (`$\varphi_{1}$` → `varphi_1`, the paper's macros expanded, `\emph{...}` and Unicode made plain); what can't be converted is left as written and counted in the report. All the formulas ok are kept, with no selection.

For the unpaired formulas, step 6 turns `data/extracted/unpaired.jsonl` into the input of `stl-nl`, a tool that writes natural-language descriptions of STL formulas: one formula per `.stl` file, in its STL grammar (bounded discrete time, closed integer intervals, every operand parenthesized). No model is called. Each formula goes through named rules, listed with an example each in `docs/normalization_rules.md`:

* the paper's own macros are expanded from its LaTeX sources (PDF formulas are already in standard notation);
* the formula is cut into tokens (LaTeX operators to STL tokens, Greek letters and subscripts to names, intervals attached to their operators) and parsed with the precedence of `stl-nl`;
* the time bounds are made closed intervals of `stl-nl`: open intervals are closed, real bounds rounded outward (the lower one down, the upper one up), a symbol alone in a bound stays a parameter (`G[0,T]`), and an operator without an interval or with an infinite upper bound gets `inf` (`G p` → `G[0,inf] p`, `F_{[a,\infty)} p` → `F[a,inf] p`); the symbols the grammar can't keep (in a bound expression such as `[t, t+5]`, or also used as a signal) get random integers from 0 to 100, the same symbol the same value everywhere in the formula;
* the result is written fully parenthesized and checked with `stlgen`, the parser of `stl-nl`.

A formula is `ok` or `rejected` (definitions of the semantics, of a grammar or of an operator, powers, functions, quantifiers, unknown commands, ...): a construct no rule covers is rejected with its reason. Some rules change the paper's meaning to keep a valid formula (random values for some bounds, a norm read as an absolute value, a call such as `Reg(4,4)` read as the name `Reg_4_4`, ...): the description `stl-nl` writes is of our formula, not the paper's. `docs/normalization_rules.md` says which, and when each was decided. Of the formulas `ok`, those with the same normalized text as an earlier one are left out, and at most 10 of each pattern go to `stl-nl`, taken from the papers in turn.

```bash
# Both files
python scripts/06_normalize_formulas.py

# Only one of them (the paired formulas don't need stlgen)
python scripts/06_normalize_formulas.py --only paired

# Other random values for the bounds that can't stay symbolic
python scripts/06_normalize_formulas.py --seed 1

# Every formula ok to stl-nl (no cap per pattern; duplicates are still left out)
python scripts/06_normalize_formulas.py --max-per-pattern 0

# Read the rejected formulas of the last run: the reasons with counts, then a sample of one reason
python scripts/06_normalize_formulas.py --show-rejected
python scripts/06_normalize_formulas.py --show-rejected function
python scripts/06_normalize_formulas.py --show-rejected "unknown_command: \overline" --limit 0
python scripts/06_normalize_formulas.py --show-rejected --only paired

# To check the translation by eye, as CSV: data/normalized/unpaired/translations.csv (the formulas kept for stl-nl:
# original, normalized, pattern) and data/normalized/paired/translations.csv (one row per requirement passage of a
# paired formula ok: original, normalized, text original, text normalized)
python scripts/inspect_normalization.py
python scripts/inspect_normalization.py --only paired
```

It needs the `stlgen` binary of `stl-nl`, built with `cargo build --release --locked --manifest-path rust/stlgen/Cargo.toml` in the `stl-nl` repository. By default it is looked for in a checkout of `stl-nl` next to this one (`../stl-nl/rust/stlgen/target/release/stlgen`); set `STLGEN_BIN` in `.env` or pass `--stlgen` for another place (only the unpaired formulas need it). It writes, in `data/normalized/unpaired/`: `stl/` (the formulas kept for `stl-nl`; the `.stl` files of an earlier run are replaced; they are numbered in input order, so a file's number can change from one run to another, and `manifest.jsonl` says which record each file is), `manifest.jsonl` (one line per input formula: `id`, `status`, `file`, `reasons`, `rules` that fired, `original`, `normalized`, `pattern` (the normalized text with the numbers written `#` and the names renamed `a`, `b`, ... in order, so that formulas differing only in numbers and names share it), `skeleton` (the coarser grouping of stl-nl's `scripts/formula_patterns.py`: the temporal and Boolean structure, each condition a Greek letter, as in `G[#,#] (φ -> F[#,#] ψ)`), `stl` as `stlgen` prints it back, `substitutions` of the symbolic bounds given random values, `rounded` bounds, `over_limits` of `stl-nl`'s selection, `selection`: `kept`, `duplicate` (with the first one's id in `duplicate_of`) or `pattern_cap` for the formulas ok) and `report.md`. In `data/normalized/paired/`: `records.jsonl` (the records of step 5 whose formula is ok, each with `normalized`, `stl` (the same formula with the parentheses `stl-nl` prints, for the final dataset), `pattern` and `skeleton` after `formula`, which stays the paper's LaTeX, and `normalized` after the `text` of each requirement), `manifest.jsonl` (as above, with no `stl` and no selection, and for the formulas ok their `requirements`: each passage's `text`, `normalized`, and what was left as written: `unreadable` math, `references`, `latex_left`, `names_not_in_formula`) and `report.md` (as above, without the selection, with the formulas that go beyond `stl-nl`'s grammar and the counts of the descriptions). The same input and seed give the same files.

| Flag | What it does |
|---|---|
| `--only NAME` | Normalize only `unpaired` or `paired` (default: both). With `--show-rejected`, the manifest to read (default `unpaired`). |
| `--seed S` | The seed of the random values of the bounds that can't stay symbolic, and of the choice per pattern (default `0`); each record's values depend only on the seed and its id. |
| `--stlgen PATH` | The `stlgen` binary (default `STLGEN_BIN`). |
| `--max-per-pattern K` | At most `K` formulas of each pattern go to `stl-nl` (default `10`, `0` for no cap), taken from the papers in turn, at random with `--seed`. |
| `--show-rejected [REASON]` | Doesn't normalize: reads `manifest.jsonl` of the last run (unpaired, or paired with `--only paired`) and prints the rejected formulas whose reason starts with `REASON` (a rule, as `function`, or a rule and what it found, as `"unknown_command: \overline"`), each with its id, original, the part the rule found and the rules applied before. A random sample drawn with `--seed`, since the manifest is ordered by paper. Without `REASON`, the reasons with their counts. |
| `--limit N` | With `--show-rejected`: how many formulas to print (default `10`, `0` for all). |

The rules are tested with `python -m pytest tests` (needs `pytest`); the test that runs `stlgen` is skipped when it isn't built.

### Step 7: Finalize the Dataset

Builds the final dataset, three sets of (description, formula) pairs, one folder each in `data/dataset/`:

| Set | Formula | Description | Folder | Judged |
|---|---|---|---|---|
| 1 | from the papers | from the papers | `set_1/` | yes |
| 2 | from the papers (`data/normalized/unpaired/stl/`) | written by `stl-nl` | `set_2/` | not yet |
| 3 | generated by `stl-nl` | written by `stl-nl` | `set_3/` | not yet |

Every formula is written as `stl-nl` prints it, so the three sets write their formulas alike: sets 2 and 3 take the text of `stl-nl`'s run, set 1 the `stl` field step 6 gives the paired formulas (the same writer, `emit.stlnl_text`, gives the text `stlgen` prints for every unpaired formula except those with `X` or `<->`, which `stlgen` rewrites and the paired formulas keep).

The descriptions of the papers are not all good training input: some only say what the formula is for, some describe another formula or only a part of it, some get a bound wrong. A judge reads each formula of `data/normalized/paired/records.jsonl` with its normalized descriptions and the meanings of its variables (from step 5), and says of each description:

* **describes** (yes / no): yes when every part of the formula (each condition, each temporal operator) has a counterpart in the description, even if a detail of it is vague; no when it only gives the purpose, covers only a part of the formula, or is about something else. A rule ("when ..., then ...", "X occurs within 10 s after Y") counts as an implicit *always* for the outermost `G` of the formula, read as `G[0,inf]`: when the formula has another interval, that interval is a time bound not given.
* **faithful**, when it describes it: **correct** (whoever knows STL would write this formula from the description, up to the names of the signals), **ambiguous** (the description fits this formula but also others: a bound or threshold not given or vague, an unclear scope), **wrong** (it contradicts the formula: another number, operator, comparison, negation).

Before the labels the judge lists the problems it finds (each difference between description and formula) and sums them up in a reason, so the labels follow from them; both are kept. The two answers give one label per description: `correct`, `ambiguous`, `wrong` or `no`. Two models judge every formula (`gemini-3.8-flash`, reasoning off, and `gpt-6-luna`, reasoning medium, as in step 5), in one call per formula with all its descriptions; where they give a description different labels, a third model (`claude-sonnet-5.5`) is asked, and its label decides when it equals one of the two. When all three differ the description is `undecided`. The prompt is in `src/dataset/judge.py`.

```bash
# A trial on 20 records (a fifth with a generic passage, a seventh with several), with every answer in
# data/processed/judgments/trial.md
python scripts/07_finalize_dataset.py --judge --trial 20

# How many calls a full run would make, and about what they cost (priced at the stored calls; no call is made)
python scripts/07_finalize_dataset.py --judge --dry-run

# Every record, then the three sets
python scripts/07_finalize_dataset.py --judge

# The three sets again, set 1 from the stored answers, without calling a model
python scripts/07_finalize_dataset.py
```

Each answer is appended to `data/processed/judgments/answers.jsonl` as it arrives, so an interrupted run continues where it stopped; a stored answer is asked again only when what the model reads changes (formula, descriptions, variable meanings, prompt), or when it failed its check (not the JSON asked, a description missing, `faithful` given for a description judged `no`). Set 1 is written only when every description has a final label.

Sets 2 and 3 come from runs of `stl-nl`, copied by hand into the set's `stlnl_run/` folder: the run's `formulas.jsonl` (the formulas, with their AST) and `pairs.jsonl` (the descriptions). A set whose `stlnl_run/` is missing is skipped. Each set is written as `pairs.jsonl`, one row per description, and `pairs.xlsx`; the script prints the formulas the run left without a description (failed, or not reached by an interrupted run). The formulas of set 2 are linked to their paper through the `.stl` file of step 6 they were read from (`source.path` in `formulas.jsonl`), checked to hold the same text; a formula that isn't linked is counted and kept, with no paper.

`data/dataset/set_1/` holds one row per description: `pairs.jsonl` (correct), `pairs_ambiguous.jsonl` (ambiguous), `dropped.jsonl` (wrong, no, undecided), and `pairs.xlsx` with one sheet each (frozen header, filters on every column), to check them by eye. Each row has:

| Field | What it holds |
|---|---|
| `id` | The pair: `<record id>:D<n>` (set 1, the n-th description of the record), `<record id>:R<n>` (set 2, the n-th description `stl-nl` wrote), `stlnl_<source index>:R<n>` (set 3) |
| `set` | The folder name |
| `nl`, `stl` | The description and the formula as `stl-nl` prints it (`nl` is the training input, `stl` the target) |
| `formula_id` | The record of step 5 the formula comes from (sets 1 and 2), `stlnl_<source index>` (set 3) |
| `stlnl_formula_id` | `stl-nl`'s id of the formula, a hash of its AST (sets 2 and 3) |
| `pattern`, `skeleton` | As in step 6 (no pattern for set 3; the skeleton of sets 2 and 3 is computed from `stl-nl`'s AST) |
| `judge` | `label`, `how` (agreed, decided by the third model, all three models differ) and `answers`: each model's label, reason and problems; `null` while the set isn't judged |
| `signals` | Checks made without a model, recorded only, not filters: `names_not_in_formula` (from step 6; set 1 only) |
| `original_stl`, `original_nl` | The formula and the description as the paper writes them (LaTeX; `original_nl` set 1 only) |
| `kind`, `domain`, `paper_id`, `license_tier`, `license`, `source_type` | From step 5 (set 3: only `domain`, from `stl-nl`) |
| `stlnl_pattern_id` | The pattern `stl-nl` generated the formula from (set 3) |

| Flag | What it does |
|---|---|
| `--judge` | Calls the models on the descriptions without a stored answer, then writes the dataset. Without it, the dataset is written from the stored answers. |
| `--trial N` | With `--judge`: only `N` records, chosen at random with a fixed seed; writes `trial.md` and not the dataset. |
| `--dry-run` | With `--judge`: prints the calls a run would make and their cost, priced at the average of the stored calls of each model (the third model on the share of records it was asked about so far). |
| `--budget D` | Dollars after which no new call is started (default `10`). |
| `--workers N` | Calls made at the same time (default `8`). |

## Data Schema (`data/corpus.json`)

`data/corpus.json` is a JSON object keyed by paper ID. The ID is the OpenAlex work ID (`W...`) or, for preprints found only through the arXiv keyword search, `arxiv_<arxiv id>`. Each entry tracks discovery provenance, local file state, license resolution and formula estimates:

```json
{
  "W1511164163": {
    "paper_id": "W1511164163",
    "openalex_id": "https://openalex.org/W1511164163",
    "arxiv_id": "1409.1234",
    "doi": "https://doi.org/10.1007/...",
    "title": "Learning and Designing Stochastic Processes from Logical Constraints",
    "year": 2015,
    "cited_by_count": 42,
    "is_oa": true,
    "alternate_ids": [],
    "discovery": {
      "methods": ["citation_hop_1", "openalex_kw:Signal Temporal Logic"],
      "hop_distance": 1,
      "parent_ids": ["W1547304883"],
      "expanded_hop_2": true
    },
    "urls": {
      "eprint_source": "https://export.arxiv.org/e-print/1409.1234",
      "pdf_mirrors": ["https://arxiv.org/pdf/1409.1234"]
    },
    "lookups": {
      "semantic_scholar": {"status": "found", "checked_at": "2026-10-12"}
    },
    "local_files": {
      "status": "downloaded_latex",
      "path": "data/raw/latex/W1511164163"
    },
    "license_info": {
      "effective_license": "cc-by-4.0",
      "effective_licenses_all": ["cc-by-4.0"],
      "effective_source": "tex_source",
      "tier": "permissive_cc",
      "has_conflict": false,
      "sources": {
        "openalex_locations": [],
        "tex_source": ["cc-by-4.0"],
        "arxiv_oai": ["http://creativecommons.org/licenses/by/4.0/"],

      }
    },

      "concrete": 12,
      "symbolic": 3,
      "formulas_concrete": 7,
      "formulas_symbolic": 2
    }
  }
}

```

| Field | Notes |
|---|---|
| `alternate_ids` | IDs of other entries that were merged into this one as duplicates (e.g. the preprint record of a published paper). A later crawl resolves them to this entry instead of adding them again. |
| `alternate_dois` | DOIs of the merged entries, when they differ from `doi`. |
| `discovery.methods` | How the paper was found: `citation_hop_1`, `citation_hop_2`, `openalex_kw:<keyword>`, `arxiv_kw:<keyword>`. A paper can have several. |
| `discovery.hop_distance` | `1` or `2` for papers from the citation crawl, `null` for papers found only by keyword. |
| `discovery.parent_ids` | The papers of the previous hop that this paper cites (the seed papers for Hop-1). |
| `discovery.expanded_hop_2` | Set on Hop-1 papers whose citing papers have already been fetched. |
| `lookups` | Written by the enrichment of Step 1: one entry per service asked (`semantic_scholar`, `arxiv_title`, `hal`), with `status` `found`, `not_found` or `no_answer` and the date of the answer. A service with no entry was not asked, either because it was not needed (for example the arXiv title search for a paper that has an arXiv ID) or because the enrichment has not reached the paper yet. |
| `local_files.status` | `pending` (to be tried by Step 2), `downloaded_latex`, `downloaded_pdf` or `unavailable`. |
| `local_files.failure_reason` | Only for `unavailable` papers; see the failure reasons under Step 2. |
| `license_info` | Written by Step 3. `effective_source` is `tex_source`, `pdf_metadata`, `arxiv_oai`, `openalex_locations` or `none`. |
| `formula_estimates` | Written by Step 4, for downloaded papers only. `concrete` and `symbolic` count temporal operators with numeric and with parametric time bounds. `formulas_concrete` counts the formulas holding at least one concrete operator, `formulas_symbolic` the formulas whose bounded operators are all parametric. |

### License Tiers

Every paper is categorized into one of four legal tiers:

1. **`permissive_cc` (`CC0`, `CC-BY`, `CC-BY-SA`, public domain):** Safe for verbatim redistribution and commercial/academic use with attribution.
2. **`restricted_cc` (`CC-BY-NC`, `CC-BY-ND`):** Permitted for non-commercial academic research; requires paraphrasing if used in derivative commercial datasets.
3. **`custom_or_arxiv` (`arXiv non-exclusive`, HAL, institutional repository):** Governed by Text & Data Mining (TDM) research exceptions; mathematical formulas are non-copyrightable facts, and natural language context should be normalized/paraphrased before redistribution.
4. **`unspecified`:** License not declared in metadata or source files.
